# 微观房源搜集与本地复用

## 默认任务与筛选口径

柏林是默认重点城市。默认硬条件：柏林住宅产权公寓、住宅挂牌房价严格低于 €500,000、Wohnfläche 严格大于 40 m²、**建筑实际建造年份在 2010 年之后**。不限定首次销售：开发商新盘和符合建造年份的二手房都搜索。2010 年本身不满足“2010 年以后”；用户修改阈值时同步更新 `Output/micro/listings.json` 的 criteria。房价预算只指住宅挂牌价；强制购买的车位、厨房及交易税费另列，不暗中并入或忽略。

已建房屋以原始建筑建造年份 `year_built` 判断，不能用装修/现代化年份代替。未建成期房如果项目页明确给出 2010 年以后的预计交付年，则先作为“期房-待交付”保留在候选表，`year_built` 保持空白，`planned_completion_year` 单列。实际建造年及交付日期最终仍要核实。两个年份均无法确认时标“建造年待核”，不计入已确认符合年份的房源。已知建造年份不满足条件者排除，但保留历史观察。

先在检索结果中用价格、面积、建造年做初筛，再核对单套页面并入库。只搜公开页面；不可绕过登录、验证码、付费墙或反爬机制。单套链接不可访问时，可记录项目页的明确单元示例，但标记 `source_level=项目页单元示例`。搜索摘要只作为线索，不直接入库。

## 信息源顺序

1. [ImmoScout24](https://www.immobilienscout24.de/) 与 [Immowelt](https://www.immowelt.de/)：检索 Berlin、Wohnung kaufen、价格/面积限制，并覆盖开发商销售与既有房屋转售；核对页面的 Baujahr、Wohnfläche、价格和房源 ID。
2. 开发商官网及 [Neubaukompass Berlin](https://www.neubaukompass.de/neubau/berlin/)：补充期房及未售新盘，区分计划交付年与实际建造年。
3. 对来源冲突：单套页面明确价格栏优先于标题；较新项目页与较旧单套页价格不同则标记，优先复核。项目总价/面积区间不能拆成虚构单套。仅“Erstbezug nach Renovierung”“neuwertig”不能证明建筑在 2010 年之后建造。

每轮至少尝试主要平台和开发商源，记下不能访问的平台与检索范围。公开挂牌可见不代表仍可售，不自动联系、询价或提交资料。

## 唯一本地数据库

- `Output/micro/listings.json`：价格和面积满足条件的当前房源候选库；有实际建造年份、期房预计交付年或待核状态。以平台房源 ID 或项目+单元唯一键去重。
- `Output/micro/observations.jsonl`：追加价格、面积、建造年/预计交付年、页面状态及观察日历史。
- `Output/micro/batches/`：增量入库批次，保留检索证据。
- `Output/micro/rent_benchmarks.json`：官方 IBB 2025 年各区挂牌净冷租中位数与来源。
- `Output/micro/柏林房源筛选.xlsx`：从本地数据库生成的工作簿，含建造年份、房龄、预计交付年、年份核验、租售测算及价格观察。

**优先读取本地库。** 重新生成 Excel 或改变排序不需要联网或重新下载租金 PDF。定期更新只核查旧房源变化并寻找新增房源，将新观察批次交给 `registry.py ingest`。未查到旧房源不能自动判定售出，保留上次观察日期；跨平台去重须有单套证据，不能仅因面积相同合并。

从项目根目录运行：

```powershell
./reference/micro/run.ps1 -Action Verify
./reference/micro/run.ps1 -Action Ingest -Batch ./Output/micro/batches/新批次.json
./reference/micro/run.ps1 -Action Build
```

批次 JSON 是数组或包含 records 数组的对象。每条需含 id、city、district、project、unit、platform、url、price_eur、area_sqm、rooms、observed_on；已建房屋填 `year_built`，期房填 `planned_completion_year`，未知则两者留空并解释。 `sale_type` 只作信息字段，不参与硬筛选。入库先检查严格边界；超价、面积不符或已知建造年过旧的房源退出当前清单，但观察历史保留。每轮验证 ID 唯一、年份口径、租金映射、公式与链接。

## 计算与解释

- 单价：挂牌住宅房价 ÷ 居住面积。
- 房龄：工作簿统计年 − 实际建造年；建造年份未知或仅有预计交付年时留空。
- 粗略月净冷租：居住面积 × IBB 同区 2025 挂牌净冷租中位数（€/㎡/月）。
- 年毛租售比：粗略月净冷租 × 12 ÷ 挂牌住宅房价。
- 房价租金比：挂牌住宅房价 ÷（粗略月净冷租 × 12）。

租金计算只是**区域挂牌租金情景**，不是该套住宅可合法收取的租金或净收益；未考虑空置、不可转嫁 Hausgeld、维修、交易税费、贷款、税收与车位。二手房尤其要核查租约、WEG 财务与房屋维修。柏林适用的租赁规定若用于具体投资结论，需在当期重新核实。

## 其他城市

新增城市时单独登记币种、行政区、租金基准和筛选条件；不把柏林租金或法规套用给其他城市。输出仍放在本项目 `Output/`，优先用当地已存数据库。

## 全量检索与覆盖验收

用户要求“所有符合条件房源”时，不能用搜索引擎索引、随机样本或单页结果代替平台全量。先确认地理范围是 Bezirk Mitte（含六个 Ortsteil）还是 Ortsteil Mitte、邮区 10179；记录每个平台的原始查询链接、硬条件、筛选后站内总数与查询时间。

按平台原生筛选取得结果后，从第一页持续翻到末页，逐页保存房源 ID 与链接、结果数、页码和时间。逐一核对面积、原建筑 Baujahr、价格及当前页面状态；建造年未公开者进入“待核”组，不能悄悄丢弃。项目总览的“N passende Wohneinheiten”必须展开到具体单元后才算入单套房；不同单元不合并。跨平台按房源 ID、地址、项目、楼层、面积和其他单套证据去重。

每轮在 Output 对应快照写 coverage.json：平台、筛选 URL、平台显示总数、可遍历页数、实际完成页数、原始 ID 数、去重后条数、已核实合格数、年份待核数、失效数及受阻原因。只有全部目标平台结果页已遍历、平台计数与抓取 ID 数可解释、所有 ID 已核验或明确列为待核、跨平台去重完毕时，才可标“全量（在所列平台与时点内）”。否则标题、Excel 首页和答复均标“未完成/已核实子集”，不能由少量样本推断剩余区域无房。

验证码、登录、付费墙或反爬阻断时，停止该平台的自动采集，不规避验证；保存已取得的覆盖证据，并说明要完成全量还需正常浏览器访问或获授权的数据导出。没有这些条件时不得承诺穷尽全网。
